# Ollama / LLM Connector Plan

Last updated: 2026-05-20

This document is the planning and brainstorming record for adding a private
Ollama-backed LLM module to the Oura dashboard. It is intentionally design-level:
no implementation has been done yet.

## Current environment

The private LLM sandbox is reachable from the development machine and intended
to be reachable from the Oura dashboard server over the private network.

| Setting | Value |
|---|---|
| Sandbox host | `neolinux` |
| Ollama base URL | `http://neolinux:11434` |
| API tested | `GET /api/tags` |
| Access pattern | Dashboard server calls Ollama server-side |

Do not call Ollama directly from browser-side UI code. The Blazor Server app
should hide LLM calls behind server-side services so prompts, model names,
network endpoints, request logging, response caching, and future safeguards stay
private and configurable.

## Product goals

The LLM should help interpret private health dashboard data without replacing
the dashboard's numeric views. It should explain patterns, summarize recent
context, and make the UI more readable, while keeping uncertainty and
non-diagnostic language explicit.

Important boundaries:

- The dashboard remains the source of truth for metrics, charts, and raw data.
- The LLM explains, summarizes, and suggests observations; it does not invent
  measurements or make medical claims.
- Generation must be optional and resilient because the Ollama server may be
  offline, slow, overloaded, or model-loading.
- Stored responses are useful UI artifacts, not canonical health records.
- Production/task-oriented LLM runs should store all request and response
  details needed for replay and debugging.
- A separate sandbox page should allow prompt/model experiments without writing
  request/response rows to the database.

## Use case discovery

### First narrow use case: night explanation

Route: `/night/{name}/{day}`

The user clicks a button such as "Generate LLM note". The app sends one night's
typed metrics plus weather context to the LLM and stores the result. The UI then
shows the latest stored note, generation time, model, latency, and any error.

Value:

- Uses already-loaded `NightData`, `NightMetrics`, and `WeatherNightContext`.
- Easy to verify manually against the page.
- Limited prompt size and blast radius.
- Good place to learn latency and quality differences between models.

Expected output:

- 3-6 concise bullets or a compact paragraph.
- Separate "what the data shows" from "possible interpretation".
- Include uncertainty and missing-data caveats.
- Avoid diagnosis or treatment instructions.

### Next use cases

| Use case | Scope | Notes |
|---|---|---|
| Morning briefing | Home page, both users, last night | Short digest for daily reading. Should reuse persisted night notes when possible. |
| Trend explanation | User page, 7/14/30/90 days | Explain directionality and distribution changes, not single-day scores. |
| Compare explanation | Compare page, Boo vs Maa over same range | Carefully phrase shared context without implying causation. |
| Raw JSON explainer | Raw page | Help understand what a raw API field means, but never send tokens/secrets. |
| Pattern question | Future chat-like UI | User asks "what changed in the last 30 days?" over selected data. |
| Data quality note | Sync/debug pages | Explain missing weather/Oura data and likely causes. |

### Later exploratory use cases

- "What should I inspect next?" suggestions linked to existing dashboard pages.
- Automatic weekly summary generated by background job.
- Prompt/model comparison view for testing local models.
- Editable per-user interpretation notes, e.g. known baselines or preferences.
- RAG-like retrieval over stored historical summaries and selected metrics.

### Sandbox use case

Route candidate: `/llm-sandbox` or hidden/debug route `/debug/llm-sandbox`

The sandbox is for manually testing prompts, model parameters, and Ollama
availability without creating normal `LlmInteraction` rows. It should be clearly
separate from production summaries.

Sandbox capabilities:

- Select model and generation parameters.
- Edit system prompt and user prompt directly.
- Optionally load a canned sample input, such as the current night page payload.
- Run the prompt and show raw response, latency, status, and error.
- Show the exact HTTP-equivalent request payload sent to Ollama.
- Copy a successful prompt into the configured/default prompt area later.

Sandbox non-goals:

- Do not automatically persist request/response rows.
- Do not affect prompt versions unless the user explicitly saves a prompt.
- Do not run automatically on page load.
- Do not become the primary user-facing health interpretation UI.

Optional later feature: store sandbox runs in a separate `LlmSandboxRuns` table
behind an explicit "save this run" button. Keep this distinct from
`LlmInteraction` so experiments do not pollute production history.

## Configuration

Add an `Llm` section in `/srv/oura-dashboard/appsettings.json` for production
and `appsettings.Local.json` for development.

```json
"Llm": {
  "Enabled": true,
  "BaseUrl": "http://neolinux:11434",
  "Model": "llama3.1:8b",
  "TimeoutSeconds": 60,
  "ConnectTimeoutSeconds": 5,
  "MaxConcurrentRequests": 1,
  "MaxPromptChars": 24000,
  "MaxResponseChars": 8000,
  "RequestCacheTtlHours": 168,
  "KeepAlive": "10m",
  "Temperature": 0.2,
  "TopP": 0.9,
  "TopK": 40,
  "RepeatPenalty": 1.1,
  "NumPredict": 700,
  "NumCtx": 8192
}
```

Equivalent environment variables, if needed for container deployment:

```text
Llm__Enabled=true
Llm__BaseUrl=http://neolinux:11434
Llm__Model=llama3.1:8b
Llm__TimeoutSeconds=60
Llm__ConnectTimeoutSeconds=5
Llm__MaxConcurrentRequests=1
Llm__Temperature=0.2
Llm__NumPredict=700
```

### Option meanings

| Option | Purpose | Initial value |
|---|---|---:|
| `Enabled` | Master switch; UI disables generation when false. | `false` in sample, `true` locally |
| `BaseUrl` | Ollama endpoint. | `http://neolinux:11434` |
| `Model` | Default model for all tasks. | `llama3.1:8b` |
| `TimeoutSeconds` | Whole request timeout. | `60` |
| `ConnectTimeoutSeconds` | Fast failure when server is unreachable. | `5` |
| `MaxConcurrentRequests` | Prevent local model overload. | `1` |
| `MaxPromptChars` | Guardrail against huge prompts. | `24000` |
| `MaxResponseChars` | Guardrail before storing/displaying. | `8000` |
| `RequestCacheTtlHours` | How long an identical prompt can reuse stored output. | `168` |
| `KeepAlive` | Ollama keep-alive hint to avoid repeated model unloads. | `10m` |
| `Temperature` | Low creativity for health-data summaries. | `0.2` |
| `TopP` | Sampling control. | `0.9` |
| `TopK` | Sampling control. | `40` |
| `RepeatPenalty` | Reduce repeated phrasing. | `1.1` |
| `NumPredict` | Maximum generated tokens. | `700` |
| `NumCtx` | Context window hint. | `8192` |

The first implementation can bind all fields even if only a subset is sent to
Ollama. That keeps future tuning config-only.

## Target architecture

| Component | Project | Responsibility |
|---|---|---|
| `LlmOptions` | `OuraDashboard.Web` or shared later | Bind and validate `Llm` config. |
| `ILlmClient` | `OuraDashboard.Web.Services.Llm` | Provider-neutral completion/chat interface. |
| `OllamaLlmClient` | `OuraDashboard.Web.Services.Llm` | Calls Ollama `/api/chat` or `/api/generate`. |
| `LlmRequestStore` | `OuraDashboard.Web.Services.Llm` | Persists request/response/error rows. |
| `LlmPromptStore` | `OuraDashboard.Web.Services.Llm` | Loads DB prompt overrides and active versions. |
| `PromptCatalog` / `PromptResolver` | `OuraDashboard.Web.Services.Llm` | Resolves system/task/user prompts from DB plus defaults. |
| `LlmHealthService` | `OuraDashboard.Web.Services.Llm` | Fast status/model check for UI. |
| `LlmSandboxService` | `OuraDashboard.Web.Services.Llm` | Runs ad hoc prompts without normal interaction persistence. |
| `NightLlmService` | `OuraDashboard.Web.Services` | Builds night-summary prompts from typed domain data. |
| `TrendLlmService` | Later | Builds trend prompts from overview rows. |
| Razor pages | Web UI | Trigger jobs and display stored outputs/status. |

The UI should depend on domain services, not on Ollama primitives. For example,
`NightDetail.razor` should ask `NightLlmService` for a note; it should not build
an Ollama request itself.

### Suggested service flow

1. Razor page asks domain LLM service for existing note and generation status.
2. User clicks generate.
3. Domain LLM service builds a normalized input object from typed dashboard data.
4. Service computes an input hash from prompt key/version, model, parameters,
   user, date/range, and normalized input JSON.
5. Store checks whether a successful matching response already exists.
6. If cache hit is acceptable, return stored response.
7. Otherwise insert a `Running` request row.
8. Call `ILlmClient` with cancellation and concurrency limit.
9. Update row to `Succeeded`, `Failed`, `TimedOut`, or `Cancelled`.
10. UI displays the latest row; generation failures do not break the page.

## Ollama API choice

Prefer `/api/chat` for prompt separation:

- `system` message: global safety and style rules.
- `user` message: task-specific instructions plus structured data.
- Optional future `assistant`/`user` turns for chat-like interactions.

Use `stream: false` for the first version. Streaming can be added later if
latency feels bad in the UI, but persisted responses and simpler error handling
are easier with non-streaming calls.

Representative request shape:

```json
{
  "model": "llama3.1:8b",
  "stream": false,
  "keep_alive": "10m",
  "messages": [
    { "role": "system", "content": "..." },
    { "role": "user", "content": "..." }
  ],
  "options": {
    "temperature": 0.2,
    "top_p": 0.9,
    "top_k": 40,
    "repeat_penalty": 1.1,
    "num_predict": 700,
    "num_ctx": 8192
  }
}
```

## Failure and slowness design

The connector must assume Ollama is a best-effort dependency.

### Failure modes to handle

| Failure | Expected behavior |
|---|---|
| `Llm:Enabled=false` | Hide or disable generate buttons; show existing stored notes if useful. |
| DNS/connect failure | Mark request failed quickly; page remains usable. |
| Ollama offline | Store failure row with concise error; show retry button. |
| Model missing | Store clear model error; health UI lists available models if reachable. |
| Model load is slow | Show "running" state; allow request timeout. |
| Request timeout | Mark `TimedOut`; user can retry with smaller/faster model. |
| HTTP 5xx | Mark failed; do not retry aggressively inside page request. |
| Malformed response | Mark failed with parse error; keep raw response only if useful and safe. |
| User navigates away | Cancellation should not corrupt DB row; mark cancelled or let background complete later. |
| Duplicate clicks | Return existing running row or enforce single active request per cache key. |

### Runtime behavior

- Use an `HttpClient` registered through `IHttpClientFactory`.
- Set a short connect timeout and a longer total request timeout.
- Use `CancellationToken` from Blazor action.
- Limit concurrency with `SemaphoreSlim` or a small channel. Start with one
  concurrent request because local models can saturate CPU/RAM.
- Do not block page loading on generation. Loading existing stored notes should
  be cheap; generation should be explicit.
- For first version, do not auto-retry long generations. A retry can double
  server load and worsen slowdowns. Manual retry is clearer.
- Log warnings through normal logging and store user-visible failure state in DB.

### UI states

Each LLM panel should have explicit states:

- Disabled: LLM not configured.
- No response yet: show generate button.
- Running: show spinner/progress text and elapsed time if practical.
- Succeeded: show response, generated timestamp, model, and latency.
- Failed/timed out: show short error, retry button, and possibly last successful
  response if one exists.
- Stale: stored response exists but input/prompt/model changed; allow regenerate.

## Prompt strategy

Use versioned prompt keys from the start. Do not treat prompts as anonymous
strings; reproducibility matters once responses are stored.

### Prompt source model

Use layered prompt sources:

1. Code or appsettings defaults provide safe bootstrapping prompts.
2. Database prompt records can override defaults after the UI exists.
3. Production interactions always store the resolved prompt messages that were
   actually sent to the model.

This gives the best mix of reliability and editability:

- The app can start with no DB prompt rows.
- Defaults can be deployed through config/code.
- UI-edited prompts can be versioned and activated without redeploying.
- Old generations remain reproducible because every interaction stores the final
  resolved messages.

Suggested appsettings shape:

```json
"LlmPrompts": {
  "DefaultSystemPrompt": "You are a private health dashboard assistant...",
  "DefaultUserContextByName": {
    "Boo": "Use concise, direct language for Boo.",
    "Maa": "Use concise, direct language for Maa."
  }
}
```

Keep long defaults in appsettings only if the operational workflow is
comfortable. If the strings become hard to maintain in JSON, move defaults to
code constants or content markdown files and let DB rows remain the editable
override layer.

### Prompt keys

| Prompt key | Scope |
|---|---|
| `shared.health_dashboard.system.v1` | Global assistant behavior and safety. |
| `person.boo.context.v1` | Stable Boo-specific preferences/baselines. |
| `person.maa.context.v1` | Stable Maa-specific preferences/baselines. |
| `night.summary.v1` | One-night explanation. |
| `trend.summary.v1` | 7/14/30/90 day trend explanation. |
| `compare.summary.v1` | Boo/Maa comparison explanation. |
| `morning.briefing.v1` | Home-page daily digest. |

### Shared system prompt principles

- You are a private health dashboard assistant.
- Explain measurements from the provided data only.
- Do not diagnose, prescribe, or claim causation.
- Separate observations from possible interpretations.
- Mention missing or weak data when relevant.
- Prefer concise, practical language over long medical explanations.
- Use the dashboard's custom metrics, especially RRS, HR above 75%, HR
  settling, HRV direction/distribution, restorative sleep, respiration, weather
  context, and recent trend windows.
- If the data does not support a claim, say so.

### Per-user prompts and memory

Start with static, editable per-user context prompts. These can live in code or
markdown files for v1, then move to DB if editing in the GUI becomes valuable.

Potential per-user context:

- Preferred name: Boo / Maa.
- Known interpretation preferences: concise, direct, no generic wellness advice.
- Baseline notes: typical HRV/HR ranges if explicitly chosen later.
- Known caveats: Oura quirks, illness/travel notes, alcohol/caffeine tags if
  those are added later.

Avoid hidden, unreviewable memory in the first version. For health-adjacent
data, "memory" should be explicit and inspectable. A good v1 is:

- `LlmUserMemories` table or config file with enabled entries.
- Each memory has text, scope, created/updated time, and active flag.
- Prompt builder injects only active memories for the relevant user.
- UI later allows viewing/editing/deleting memory entries.

### Prompt persistence and overrides

Persist system prompts and user prompts as first-class records once the first
production flow is implemented. Defaults may live in appsettings/code, but DB
records should be the long-term source of active prompt versions.

Proposed entity: `LlmPrompt`

| Column | Notes |
|---|---|
| `Id` | Primary key. |
| `Key` | Stable key, e.g. `shared.health_dashboard.system`. |
| `Version` | Integer version. |
| `Scope` | `system`, `task`, `user_context`, `memory`, `sandbox_template`. |
| `UserId` | Optional; set for user-specific prompts. |
| `Name` | Human-friendly display name. |
| `Content` | Prompt text. |
| `IsActive` | Active version for this key/scope/user. |
| `IsDefault` | True for seeded/imported default rows if useful. |
| `CreatedAtUtc` / `UpdatedAtUtc` | Audit fields. |
| `CreatedBy` / `UpdatedBy` | Optional local username/source. |
| `Notes` | Why this prompt version exists. |

Prompt rules:

- Never update prompt text in place for active prompts used by production
  interactions. Create a new version instead.
- Only one active prompt should exist for a given `(Key, Scope, UserId)` tuple.
- Production interactions store both prompt references and resolved
  `MessagesJson`.
- Appsettings/code defaults are fallback prompts, not enough for reproducibility
  by themselves.
- UI should support activating/deactivating versions, not deleting history.

Prompt resolution order:

1. Active DB prompt for exact key/scope/user.
2. Active DB prompt for key/scope with no user.
3. Appsettings/code default.
4. Hard failure for production generation if a required prompt is missing.

Sandbox prompt editing can bypass this resolver for ad hoc tests, but saving a
sandbox prompt should create a new inactive `LlmPrompt` version unless the user
explicitly activates it.

### Data access policy

The LLM should receive compact, normalized summaries rather than raw database
rows by default.

For night summary:

- Send scalar metrics, computed custom metrics, key weather context, and compact
  time-series descriptors.
- Do not send full raw Oura JSON unless the use case specifically requires it.
- Do not send API tokens or app configuration.

For trends:

- Send window aggregates: min/median/max, recent direction, distribution buckets,
  count of missing days, notable outliers.
- Avoid dumping every sample unless the model needs it.

## Persistence design

Storing prompts and responses is part of the first real implementation, not an
afterthought. It supports slow models, repeatability, GUI history, debugging,
and prompt/model comparison.

Decision: store all production LLM interactions, including failures. The only
exception is the explicit sandbox area, where runs are not stored by default.

### Main request table

Proposed entity: `LlmInteraction`

| Column | Type | Notes |
|---|---|---|
| `Id` | `long` | Primary key. |
| `Scope` | `string` | `night`, `trend`, `compare`, `morning`, `freeform`. |
| `UserId` | `int?` | Null for compare/global. |
| `UserNameSnapshot` | `string?` | Display resilience if user changes. |
| `Day` | `DateOnly?` | Night/day-specific request. |
| `StartDay` / `EndDay` | `DateOnly?` | Range requests. |
| `PromptKey` | `string` | e.g. `night.summary.v1`. |
| `PromptVersion` | `int` or part of key | Keep explicit if useful. |
| `Model` | `string` | Actual model used. |
| `Provider` | `string` | `ollama`. |
| `ParametersJson` | `jsonb` | Temperature, top_p, num_ctx, etc. |
| `InputHash` | `string` | Unique-ish hash for cache/stale detection. |
| `InputJson` | `jsonb` | Normalized metric input, not raw secrets. |
| `MessagesJson` | `jsonb` | System/user messages for reproducibility. |
| `ResponseText` | `text?` | Human-readable response. |
| `ResponseJson` | `jsonb?` | Future structured output. |
| `RawRequestJson` | `jsonb?` | Provider request payload after sanitization. |
| `RawResponseJson` | `jsonb?` | Provider response payload after sanitization. |
| `Status` | `string` | `running`, `succeeded`, `failed`, `timed_out`, `cancelled`. |
| `ErrorCode` | `string?` | `connect_failed`, `timeout`, `http_500`, etc. |
| `ErrorMessage` | `text?` | Short sanitized error. |
| `PromptTokens` / `CompletionTokens` | `int?` | If provider returns them. |
| `LatencyMs` | `int?` | End-to-end call duration. |
| `CreatedAtUtc` | `DateTimeOffset` | Request created. |
| `StartedAtUtc` | `DateTimeOffset?` | Provider call started. |
| `CompletedAtUtc` | `DateTimeOffset?` | Terminal state time. |

Suggested indexes:

- `(Scope, UserId, Day, CreatedAtUtc desc)`
- `(Scope, UserId, StartDay, EndDay, CreatedAtUtc desc)`
- `(InputHash, Status)`
- `(CreatedAtUtc)`

For cache safety, either:

- enforce only one `running` row per `InputHash`, or
- check for an existing running row before inserting.

Store enough raw provider data to debug, but still sanitize:

- Do not store API tokens or app secrets.
- Do not store unrelated config.
- Do store model, messages, options, keep-alive value, latency, Ollama metadata,
  and sanitized error body.
- If provider payloads become large, keep normalized `InputJson` and
  `MessagesJson` as the canonical replay data and trim raw provider blobs.

### Optional memory table

Proposed later entity: `LlmUserMemory`

| Column | Notes |
|---|---|
| `Id` | Primary key. |
| `UserId` | Owner. |
| `Scope` | `all`, `night`, `trend`, etc. |
| `Text` | Explicit memory/instruction. |
| `IsActive` | Whether injected into prompts. |
| `CreatedAtUtc` / `UpdatedAtUtc` | Audit fields. |

Do not add this until the first summary flow proves useful. Static prompt files
or appsettings entries are enough for early user context, but system/task prompt
overrides should still move to `LlmPrompt` once production generations are
stored.

### Sandbox storage policy

Default sandbox runs should be ephemeral:

- They may live in component state while the page is open.
- They should not create `LlmInteraction` rows.
- They should not affect cache/stale logic.
- They should still use the same `ILlmClient` and options validation as
  production calls.

If saving sandbox runs becomes useful, add an explicit `Save run` button and
write to a separate table such as `LlmSandboxRun`.

Proposed later entity: `LlmSandboxRun`

| Column | Notes |
|---|---|
| `Id` | Primary key. |
| `Model` | Model used. |
| `ParametersJson` | Generation options. |
| `MessagesJson` | Prompt messages. |
| `ResponseText` / `ResponseJson` | Result. |
| `Status` / `ErrorMessage` | Outcome. |
| `LatencyMs` | Timing. |
| `CreatedAtUtc` | When saved. |
| `Notes` | Manual note about the experiment. |

## GUI design ideas

### Night page panel

Add a compact panel below the verdict/weather area or near custom metrics:

- Header: "LLM note"
- Status badge: disabled / running / generated / failed / stale
- Generate/regenerate button
- Response body
- Metadata line: model, generated time, latency, prompt key
- Error line with retry button when failed

Keep it visibly secondary to the actual metrics. The dashboard data should stay
first.

### Sync/debug page

Add an LLM diagnostics section later:

- Config enabled/disabled.
- Base URL host only, not secrets.
- Current model.
- Health check result.
- Available models from `/api/tags`.
- Last 5 failures.

### Prompt management page

Add later, after the first working production prompt:

- List active system, task, and per-user prompts.
- Show prompt version history.
- Create a new version from an existing prompt.
- Activate/deactivate versions.
- Show where each prompt is used.
- Link to recent interactions generated with a prompt version.

Do not allow silent edits to active prompt text. Versioning is the protection
against confusing old stored responses.

### Sandbox page

Add a hidden/debug page for manual experiments:

- Freeform system prompt textarea.
- Freeform user prompt textarea.
- Model and parameter controls.
- Optional selector for canned context payloads.
- Run button with timeout/error display.
- Raw request and raw response viewers.
- Optional "save as prompt draft" button, separate from production generation.

This page should be visually and operationally marked as sandbox/debug. It
should not imply that sandbox output is part of the health dashboard history.

### History view

Later, a simple `/llm` or tab on `/raw` could show stored interactions:

- Filter by user, scope, status, model, prompt key.
- Inspect input JSON/messages/response for debugging.
- Compare two model outputs for the same input hash.

- Choose first prompt shape and response format.
- Decide whether the first generation runs inline from button click or through

- Add `LlmPrompt` entity and migration for versioned prompt overrides.
- Add `LlmRequestStore` for insert/update/query.

## Open design questions

1. Should v1 responses be plain text only, or should the model produce a small
   JSON object such as `{ "summary": "...", "bullets": [], "caveats": [] }`?
   Recommendation: plain text first; structured output later if the UI needs
   separate fields.
2. Should generation run inline from Blazor events or through a background
   queue?
   Recommendation: inline first with timeout and DB status; queue later.
3. Should prompt templates live in C# constants or markdown files?
   Recommendation: C# constants for v1, because versioning and tests are easy.
   Markdown files are fine once prompts are edited often.
4. Should failed requests be persisted?
   Decision: yes. The GUI/debug value is high and it helps diagnose unreachable
   or slow Ollama.
5. Should memory be implemented in v1?
   Recommendation: no. Start with explicit per-user prompt context, then add DB
   memory after real usage shows what should be remembered.
6. Should old successful responses be invalidated automatically?
   Recommendation: mark stale by hash mismatch, but keep history.
7. Should prompts be editable in the UI?
   Recommendation: yes eventually, through versioned DB prompt records. Use
   appsettings/code defaults as fallback, not as the only long-term source.
8. Should sandbox runs be stored?
   Recommendation: no by default. Add explicit save-to-sandbox-history later if
   experiments need to be retained.

The smallest useful slice:

1. Add `LlmOptions`, `ILlmClient`, and `OllamaLlmClient`.
2. Add a sandbox/debug page for manual prompt and model testing without normal
   DB interaction storage.
3. Add `LlmInteraction` persistence with success/failure status.
4. Add `LlmPrompt` persistence for system/task/per-user prompt overrides.
5. Add `NightLlmService` for `night.summary.v1`.
6. Show an "LLM note" panel on `/night/{name}/{day}` behind a generate button.
7. Add diagnostics to `/sync` after the first feature works.

This gives immediate value, exercises the unstable dependency, and creates the
stored history needed for later GUI and prompt tuning.

## Operational notes

- Keep Ollama exposed only on the private network or firewall it to the
  dashboard server.
- Production dashboard runs in Docker under `docker/oura-dashboard/` and mounts
  `/srv/oura-dashboard/appsettings.json`.
- The dashboard server must be able to resolve `neolinux`; otherwise use the
  sandbox server's private IP in `Llm:BaseUrl`.
- Prefer server-side calls from .NET with configured timeouts and cancellation
  tokens.
- The app should start and work normally even when Ollama is unavailable.
